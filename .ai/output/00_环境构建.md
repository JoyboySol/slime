# slime Hybrid GDN Dense 环境构建

## 目标

为 `/mnt/ssd/lvzhihao/PostTrain/slime` 构建一个不依赖 Docker 的本地开发环境，同时满足下面三个约束：

- 训练后端使用 `/mnt/ssd/lvzhihao/PostTrain/YuLan-Pretrain`
- 推理侧使用 `/mnt/ssd/lvzhihao/PostTrain/sglang_qwen3_next_plugin`
- 最终开发环境固定为 `/mnt/ssd/lvzhihao/PostTrain/slime/.venv`

本轮文档明确拆成两条链路：

- 链路 A：从 `YuLan-Pretrain/.venv` 迁移，再修复冲突
- 链路 B：从 0 开始重建，并显式编译 `apex + flash-attn + transformer-engine`

两条链路都使用 `uv` 作为安装入口。

## 链路 A：迁移 YuLan-Pretrain/.venv，再修复冲突

### 适用场景

适合下面几种情况：

- `YuLan-Pretrain/.venv` 已经可用
- 想最快得到一个能跑 slime 的环境
- 希望复用已有的 CUDA 扩展编译结果，尽量少重编

### 1. 复制基础环境

```bash
cd $ROOT
rm -rf $VENV_DIR
rsync -a --delete $YULAN_DIR/.venv/ $VENV_DIR/
```

### 2. 修复虚拟环境内部路径

```bash
OLD="$YULAN_DIR/.venv"
NEW="$VENV_DIR"

sed -i "s|$OLD|$NEW|g" "$NEW/pyvenv.cfg"
sed -i "s|$OLD|$NEW|g" "$NEW/bin/activate"
sed -i "s|$OLD|$NEW|g" "$NEW/bin/activate.csh"
sed -i "s|$OLD|$NEW|g" "$NEW/bin/activate.fish"

for file in "$NEW/bin/"*; do
    if [ -f "$file" ] && head -n 1 "$file" | grep -q "$OLD"; then
        sed -i "1 s|$OLD|$NEW|" "$file"
    fi
done
```

### 3. 确保 uv 可用

```bash
$VENV_DIR/bin/pip install -i $UV_INDEX uv
$VENV_DIR/bin/uv --version
```

### 4. 升级 torch 栈

```bash
$VENV_DIR/bin/uv pip install \
  --python $VENV_DIR/bin/python \
  --index-url $TORCH_INDEX \
  --extra-index-url $UV_INDEX \
  torch==2.9.1 \
  torchvision==0.24.1 \
  torchaudio==2.9.1
```

建议升级后立刻检查：

```bash
source $VENV_DIR/bin/activate
python - <<'PY'
import torch
print(torch.__version__)
print(torch.version.cuda)
PY
```

### 5. 安装运行时依赖

```bash
$VENV_DIR/bin/uv pip install \
  --python $VENV_DIR/bin/python \
  --index-url $UV_INDEX \
  'ray[default]' \
  'sglang-router>=0.2.3' \
  sglang==0.5.9 \
  blobfile \
  omegaconf \
  pylatexenc \
  'mcp[cli]' \

  qwen_vl_utils \

```

### 6. 安装本地 editable 包

安装 slime：

```bash
$VENV_DIR/bin/uv pip install \
  --python $VENV_DIR/bin/python \
  --index-url $UV_INDEX \
  --editable $SLIME_DIR \
  --no-deps
```

安装插件：

```bash
$VENV_DIR/bin/uv pip install \
  --python $VENV_DIR/bin/python \
  --index-url $UV_INDEX \
  --editable $PLUGIN_DIR
```

### 7. 修复 torch 升级后的 CUDA 扩展冲突

这条链路里最真实、最典型的问题就是 `flash_attn` ABI 不兼容。

卸载旧版本：

```bash
source $VENV_DIR/bin/activate

uv pip uninstall \
  --python $VENV_DIR/bin/python \
  flash-attn flash_attn -y
```

重新编译安装：

```bash
uv pip install \
  --python $VENV_DIR/bin/python \
  --index-url $UV_INDEX \
  flash-attn==2.7.4.post1 \
  --no-build-isolation
```

如果 `apex` 或 `transformer_engine` 也失效，则直接参考下方“链路 B”的显式源码编译步骤重装。

## 本轮遇到的关键问题与解决

### 1. flash-attn 在 torch 升级后不兼容

问题现象：

```text
ImportError: ... flash_attn_2_cuda...so: undefined symbol: ...
```

问题本质：

- 升级到 `torch 2.9.1` 之后，原先的 `flash_attn` 二进制扩展仍然是按旧 torch ABI 编译的
- 因此导入时会报 undefined symbol

解决方式：

- 卸载旧版 `flash-attn`
- 用当前环境里的 torch 重新编译安装 `flash-attn==2.7.4.post1`

### 2. 编译 flash-attn 时看起来“卡住”

实际不是卡住，而是在编译 CUDA 扩展。

判断方式：

```bash
pgrep -af 'flash-attn|nvcc|c\+\+|g\+\+|ninja|cmake|ptxas|cicc'
```

如果能看到：

- `nvcc`
- `ptxas`
- `cicc`
- `ninja`

那通常就是正常编译中。

### 3. Ray 运行时环境需要补 `TORCH_CUDA_ARCH_LIST=8.0`

这条是在真实 slime RL 流程中补出来的经验。

Ray job 的 runtime env 里加入：

```bash
export TORCH_CUDA_ARCH_LIST=8.0
```

会比只在交互 shell 中导出更稳妥。

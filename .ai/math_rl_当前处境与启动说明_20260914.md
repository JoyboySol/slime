## 5. 当前主要风险

1. `train_rollout_logprob_abs_diff` 仍然不可靠，route replay B2 没有改善它。
2. B2 使用短 response，且有 `truncated_ratio=0.5`，因此不能把绝对数值直接外推到 31744 response 的正式训练；但 `1.065` 仍足以说明对齐存在问题。
3. 当前 route replay 需要进一步验证 routed experts 的 token 顺序、prompt/response 拼接边界、CP 分片顺序、layer 顺序以及 EP rank 映射。
4. 正式配置使用 `REBUILD_TRAIN_ACTORS=1` 时必须传 `SAVE_HF`。
5. TE FusedAdam 的 GPU OOM 与 route replay 是两个独立问题；不能通过 route replay 解决 optimizer 显存峰值。

## 6. 下一步建议

正式训练前建议先做一个更严格的 route 对齐诊断：

1. 保存 B2 的完整 rollout 数据，尤其是 `rollout_routed_experts`；
2. 在 actor 侧逐层比较 SGLang routed experts 与 MCore replay 输入的 shape、token 数和 expert id；
3. 分别测试 prompt-only、response-only 和完整序列的 logprob diff；
4. 验证 CP=8 下 routed experts 的分片是否与 `prepare_routed_experts_for_routing_replay` 完全一致；
5. 修复后再以 `global_batch=8` 做 A/B，最后才扩大到 `global_batch=256`。

在 route replay 指标稳定低于 `0.1` 之前，不建议把 `--use-rollout-routing-replay` 直接加入全量训练。

## 8. CP 前向差异的进一步定位（2026-09-14）

在同一份 rollout 和同一份 HF 权重上，保存了 CP=1/8 的逐 token 训练前向结果：

```text

/mnt/yulan/lvzhihao/PostTrain/outputs/yulan_moe_route_replay_cp8_debug_complete_20260914/train_0.pt
/mnt/yulan/lvzhihao/PostTrain/outputs/yulan_moe_noreplay_cp8_debug_complete_20260914/train_0.pt
```

关键事实：

1. CP=1 与 CP=8 的 8 条样本的 token、`loss_mask`、response 位置和样本顺序完全一致，因此不是 batch 拼接、response slice 或 debug 聚合造成的假象。
2. CP=1 + route replay 的逐样本平均绝对差约为 `0.025--0.054`；CP=8 + route replay 约为 `0.538--1.450`，且每个样本都明显偏大。
3. CP=8 关闭 route replay 后仍约为 `0.556--2.481`，说明主要问题是 CP=8 的模型前向本身；route replay 只能带来部分改善，不是根因。
4. 关闭 `gdn_cp_run_level_layout` 和 `gdn_cp_use_token_exchange` 后，CP=8 + replay 仍为 `0.83532459`；临时补齐 `PackedSeqParams` 的 packed/valid/cumulative metadata 后仍为 `0.83530140`。因此这两个开关及简单 metadata 缺失均不是充分解释。

所有诊断用的 optimizer 跳过逻辑和 YuLan route replay 临时修改均已恢复；YuLan-Pretrain 的原有未提交修改保持不变。

## 9. `cu_seqlens` 假设实验（2026-09-14）

为检验 Slime 在已手工 CP 重排后的 THD token 上是否错误使用了“原始长度” cumulative offsets，临时将 `data.py` 中的：

```python
torch.tensor(cu_seqlens) * cp_size
```

改成不乘 CP 的本地 offsets，并在 CP=8、route replay、同一份 rollout 下运行完整 forward/backward（optimizer 临时跳过）。结果：

```text
train/train_rollout_logprob_abs_diff = 0.8361760377883911
log: /mnt/yulan/lvzhihao/PostTrain/outputs/logs/yulan_moe_cp8_local_cu_diag_20260914c.log
```

与原始 CP=8 + replay 的约 `0.8362` 没有实质变化，故排除“仅由 `cu_seqlens * cp_size` 引起”的解释。实验中还确认：

- 不启动 SGLang、直接复用保存的 rollout 可以稳定进入 actor train；
- 前向/backward 成功，失败的 optimizer OOM 仍是独立的 TE FusedAdam state 初始化峰值；
- 本次使用的 local-cumulative-offset 诊断、optimizer skip 和 route replay 临时 hook 均已恢复。

当前 CP 根因范围进一步收敛到：CP interleaved token 的实际 partition/index 语义、attention 的 causal/ring 通信，以及 RoPE/THD 位置索引之间的组合，而不是单一 cu-seqlens 缩放或 loss 指标聚合。

## 13. YuLan 标准 THD/CP 适配实验（2026-09-14）

为验证“直接复用 YuLan-Pretrain 的 CP 实现”是否能解决问题，在 Slime 中增加了可选环境开关 `SLIME_USE_YULAN_THD_CP=1`，不修改 YuLan-Pretrain 源码。该分支：

- 每条样本按 `2*CP` 对齐后再 pack；
- 调用 YuLan 的 `get_thd_batch_on_this_cp_rank` 做 TE THD 分片；
- 同时分片 tokens、loss mask 和 padding mask；
- 在 Slime 的 YuLan Mamba model provider 中补传 `packed_seq_params`/`padding_mask` 到 GDN/MoE TransformerLayer。原 provider 之前直接丢弃了这两个 Transformer-specific 参数，因此仅替换数据切分并不能真正进入 YuLan 的标准 CP forward。

结果与发现：

1. 仅使用标准 THD 分片、未启用 replay 时，前向可以跑通，指标为 `0.8756659`；它没有把 CP=8 偏差降到 CP=1 的水平，因此“TE partition index 不一致”不是唯一根因。
2. 第一版标准 THD + replay 暴露了明确的布局错误：replay top-k 行数与 router logits 不一致（`1536/1438`）。随后补齐了每样本 alignment padding、`padding_mask` 以及 provider 参数传递。
3. 补齐后 replay 的第一 microbatch 已通过，不再出现长度断言；但第二 microbatch 在 CP collective 长时间不推进，实验被主动终止，尚未证明 CP=8 已稳定。
4. 当前结论不是“CP=8 已可用”，而是：YuLan 标准 CP 路径是必要方向，但需要继续隔离 Mamba/GDN 的 run-level CP 状态与多 microbatch 重置/同步问题。CP=1 + replay 仍是现阶段稳定基线。

本轮临时注入 YuLan route replay hook 已恢复；YuLan-Pretrain 的原有未提交修改保持不变。Slime 的标准 THD 分支仍通过环境变量关闭，未改变默认旧路径。

## 14. Block-level GDN CP 修复验证（2026-09-14）

继续追踪后确认，之前的卡点不是 rollout、route replay、loss mask 或 `cu_seqlens` 聚合，而是模型封装层级：Slime 的 `_YuLanMambaStack` 把 GDN 包成单个 `TransformerLayer`，逐层直接调用；YuLan 的 `TransformerBlock` 才实现了 GDN CP 所需的整段 layer-loop 协议，包括：

- GDN interleaved 与 sequential-chunk layout 的转换；
- 每层对应的 `valid_token_mask`/MoE padding mask；
- `gdn_cp_sequential_cu_seqlens` 和 pre-GDR plan identity 的生命周期；
- 每个 microbatch 后的 GDN runtime state 清理。

## 17. Routing replay 差异根因定位（2026-09-14）

完成了同一份 rollout、同一套 CP=8/EP=8、dynamic microbatch、2 个 microbatch 的三组对照：

| 实验 | routing replay | rollout routing replay | abs diff | 结果 |
| --- | --- | --- | ---: | --- |
| 严格第 14 节复现 | 关 | 关 | `0.04640966` | 成功 |
| actor replay only | 开 | 关 | `0.04690091` | 成功 |
| rollout route replay | 开 | 开 | `1.31236720` | 成功但严重不一致 |

因此可以排除：

- `RoutingReplay` 的 forward/backward 记录与消费机制本身；
- CP=8 下 dynamic microbatch 的一般训练流程；
- actor-only 的 replay hook。

进一步在 actor-only 的自然 MCore 路由与 rollout 路由之间做了 CP 变换后的逐层逐 microbatch 对比。以 rank 0 为例：

```text
compared=335232
mismatched=281090
element mismatch fraction=0.838494
set_mismatched_rows=73605
order_only_rows=3684
```

其他 rank 的 element mismatch 约 `0.897`。更重要的是，`set_mismatched_rows` 约占全部 token-row 的 `88%`，不是单纯 top-k 顺序不同，而是 rollout/SGLang 与 MCore 自然计算出的专家集合本身大面积不同。这个诊断使用的临时 compare hook 已在实验后移除，不会进入正常训练路径。

当前最可信的根因范围已经从“replay 状态机”收敛到“rollout 路由与 actor 路由的语义不一致”，重点包括：

1. SGLang `routed_experts` 的 token/layout 顺序与 YuLan THD CP 的 TE partition 是否完全一致；
2. SGLang EP=2 返回的 expert id 与 MCore EP=8 dispatcher 所需的全局 expert id 是否一致；
3. SGLang 与 MCore 的 sqrt-gate/router score、router dtype、top-k selection 是否完全一致；
4. rollout capture 的层号/路由行是否与 actor 的 54 个 MoE layer 顺序一致。

在这四项未验证前，不应把 `--use-rollout-routing-replay` 加入正式训练。`--use-routing-replay` 单独开启目前不会造成指标恶化，但它只会 replay MCore 自己记录的路由，不能解决 SGLang 与 actor 的训推路由差异。

## 19. 全量训练启用 train actor 释放（2026-09-14）

为避免上一轮“actor train 完成后 train actor 仍占用 GPU，随后重启 SGLang OOM”的问题，全量启动脚本进一步改为：

```text
DESTROY_ROLLOUT_ENGINES=1
REBUILD_TRAIN_ACTORS=1
SAVE_HF=${OUTPUT_ROOT}/hf/rollout_{rollout_id}
```

启用 `--rebuild-train-actors` 后，每轮 actor train 保存当前 MCore/HF 快照并真正 `ray.kill` train actor，之后才重建 SGLang；下一轮 rollout 前再从最新 HF 快照重建 actor。`SAVE_HF` 是该选项的必需参数。

脚本仍使用 `--checkpoint-retention-count 2` 和 `--checkpoint-retention-interval 20`，因此 MCore 与 HF 快照都只保留最近两个以及每 20 个 rollout 的周期性快照，不会因为每轮重建而无限占用磁盘。
